# 🥗 NutriTrack — Веб-застосунок для обліку харчування, КБЖВ та контролю здоров'я

**NutriTrack** — повнофункціональний full-stack веб-застосунок (SPA + SSR/REST API), призначений для щоденного моніторингу раціону харчування, підрахунку калорій та макронутрієнтів (білків, жирів, вуглеводів), створення власних продуктів і рецептів, сканування штрихкодів товарів камерою смартфона, а також ведення календаря циклу.

* 🌐 **Production (Render):** [https://nutritrack-cu8u.onrender.com](https://nutritrack-cu8u.onrender.com)
* 💻 **Локальне середовище:** `http://localhost:3000` (Backend + зібраний Frontend) / `http://localhost:5173` (Vite Dev Server)

## ✨ Ключовий функціонал

* **Щоденник харчування за прийомами їжі:** додавання, перегляд та видалення страв (сніданок, обід, вечеря, перекус) із миттєвим перерахунком добової норми калорій та БЖВ.
* **Пошук продуктів у реальному часі (Autocomplete):** інтеграція із зовнішньою базою **FatSecret Platform API** із debounce-оптимізацією запитів (350 мс).
* **Сканер штрихкодів камерою пристрою:** зчитування форматів `EAN-13`, `EAN-8`, `UPC-A` через задню камеру смартфона (`html5-qrcode`) або ручне введення коду з пошуком у міжнародній базі **Open Food Facts API v2** (включно з автоматичною конвертацією кДж у ккал).
* **Оцінка корисності продукту (0–10 балів):** автоматичний алгоритм аналізу співвідношення білків, жирів та вуглеводів на 100 г продукту.
* **Власна база продуктів і конструктор рецептів:** створення власних продуктів із етикетки та складання багатокомпонентних рецептів з автоматичним розрахунком енергетичної цінності готової страви на 100 г.
* **Інтерактивний календар циклу:** відстеження фаз циклу та синхронізація параметрів циклу з профілем користувача.
* **Адаптивний інтерфейс та теми оформлення:** повна підтримка світлої (`light`) та темної (`dark`) тем, адаптація під мобільні браузери iOS Safari та Android Chrome.
* **Адміністрування:** розмежування ролей (`USER` / `ADMIN`), серверна адміністративна панель для моніторингу користувачів та системних даних.

## 🔌 Документація REST API

Усі захищені маршрути вимагають активної сесії авторизованого користувача (`req.isAuthenticated()`).

| Метод | Ендпоінт | Опис |
| :--- | :--- | :--- |
| `GET` | `/auth/google` / `/auth/logout` | Вхід через OAuth та завершення сесії користувача |
| `GET` | `/api/fatsecret/search?query=...` | Пошук продуктів у базі FatSecret із поверненням КБЖВ на 100 г |
| `GET` | `/api/barcode/:code` | Пошук продукту за штрихкодом (EAN/UPC) через Open Food Facts API v2 |
| `GET` | `/api/custom-foods?query=...` | Отримання списку власних продуктів користувача |
| `POST` | `/api/custom-foods` | Створення нового власного продукту в БД |
| `DELETE` | `/api/custom-foods/:id` | Видалення власного продукту користувача |
| `GET` | `/api/recipes?query=...` | Отримання збережених рецептів користувача |
| `POST` | `/api/recipes` | Збереження нового рецепта з розрахованими БЖВ |
| `DELETE` | `/api/recipes/:id` | Видалення рецепта користувача |
| `POST` | `/api/meals/add-food` | Додавання порції продукту/рецепта до прийому їжі |
| `GET` | `/admin` | Серверна панель адміністратора (доступ лише для `role === 'ADMIN'`) |

## 📊 Звіт про виконання лабораторних робіт №1–№5

### Лабораторна робота №1. Розробка серверної частини (Backend)

* **Веб-фреймворк:** серверну частину реалізовано на базі **Node.js + Express.js** (`backend/server.js`) із модульною маршрутизацією (`routes/auth.js`, `routes/api.js`, `routes/admin.js`, `routes/barcodeRoutes.js`).
* **Робота з базою даних:** використано **Prisma ORM** для роботи з реляційною базою даних (збереження профілів користувачів, щоденних записів харчування, власних продуктів, рецептів та параметрів циклу).
* **Генерація динамічних HTML-сторінок:** налаштовано шаблонізатор **EJS** (`app.set('view engine', 'ejs')`, `views/index.ejs`) для серверного рендерингу сторінок із передачею даних поточного користувача (`user: req.user`) та адміністративної панелі.
* **Підтримка статичного контенту:** організовано роздачу статичних файлів із директорії `backend/public` (стилі, медіа, інформаційні матеріали) та зібраного клієнтського бандлу `frontend/dist`.
* **Реєстрація, логін та сесії:** інтегровано **Passport.js** (`backend/config/passport.js`) із підтримкою OAuth-автентифікації та збереженням сесій через `express-session`.
* **Збереження дій зареєстрованих користувачів на сервері:** авторизовані користувачі можуть додавати з'їдені продукти, створювати власні страви та рецепти, змінювати налаштування профілю — усі зміни персистентно записуються в БД із прив'язкою до `userId`.
* **Підтримка адміністративних користувачів:** у моделі користувача передбачено поле ролі (`USER` / `ADMIN`). Реалізовано middleware автоматичного призначення ролі `ADMIN` для облікового запису, вказаного в `ADMIN_EMAIL`, а також захищені маршрути адміністрування (`routes/admin.js`).

* **Frontend-бібліотека:** клієнтська частина розроблена як Single Page Application (SPA) на **React** зі збірником **Vite**.
* **Інтерактивне оновлення інтерфейсу:** реалізовано реактивне оновлення стану без перезавантаження сторінки — динамічний перерахунок калорій та макронутрієнтів під час перетягування повзунка ваги, миттєве фільтрування списків, перемикання вкладок (`База / Код`, `Мої продукти`, `Рецепти`), покроковий конструктор рецептів і перемикання світлої/темної теми.
* **Робота із зовнішніми Web API та сервісами:**
  * взаємодія з власним REST API бекенду через **Axios**;
  * отримання даних про продукти із загальнодоступних зовнішніх API (**FatSecret Platform API** та **Open Food Facts API v2**);
  * OAuth-авторизація через зовнішнього провайдера;
  * використання браузерного Web API камери (`MediaDevices.getUserMedia` через `html5-qrcode`) у компоненті `BarcodeScannerModal.jsx` для розпізнавання штрихкодів у реальному часі.
* **Збереження даних локально на пристрої користувача:** застосовано `localStorage` браузера для збереження користувацьких налаштувань інтерфейсу (обрана тема оформлення `light`/`dark`, локальний стан клієнта) між перезавантаженнями сторінки та сесіями.

### Лабораторна робота №3. Розробка веб-сервісів / Web API

* **Методи отримання та модифікації даних:**

* **Авторизація користувачів:** доступ до персональних ресурсів захищено перевіркою сесійної автентифікації та ізоляцією даних за ідентифікатором поточного користувача.
* **Демонстрація роботи:**
  * протестовано ендпоінти за допомогою інструментальних засобів розробки (**Chrome DevTools → Network**, **Postman / cURL**);
  * інтегровано API у веб- та мобільний клієнтський інтерфейс **NutriTrack** (включно з роботою на мобільних пристроях iOS/Android).

### Лабораторна робота №4. Розгортання та продуктивність веб-застосунків

#### 1. Середовища розгортання

Застосунок розгорнуто та протестовано у двох середовищах:

1. **Локальний сервер (`localhost`):** Express-сервер на `http://localhost:3000` із локальною базою даних та зібраним клієнтським бандлом `frontend/dist`.
2. **Публічний хмарний сервер (Render):** production-інстанс за адресою `https://nutritrack-cu8u.onrender.com` з автоматичним HTTPS (TLS), зворотним проксі та керованою базою даних PostgreSQL.

#### 2. Методика та результати вимірювання продуктивності

Вимірювання проводилися за допомогою **Google Lighthouse** (режими Mobile та Desktop) та **Chrome DevTools (Network / Performance)**:

| Метрика продуктивності | `localhost:3000` (Локальний сервер) | `nutritrack-cu8u.onrender.com` (Render, прогрітий інстанс) | Примітки |
| :--- | :---: | :---: | :--- |
| **First Contentful Paint (FCP)** | ~0.4 с | ~0.9 с | Швидке завантаження бандлу Vite |
| **Largest Contentful Paint (LCP)** | ~0.6 с | ~1.3 с | Оптимізовані SVG-іконки та CSS без важких фреймворків |
| **Time to First Byte (TTFB) для `/api/*`** | 12–25 мс | 90–180 мс | На Render після простою (Cold Start) перший запит займає ~15–25 с |
| **Пошук за штрихкодом (`/api/barcode/:code`)** | ~320 мс | ~410 мс | Залежить від часу відповіді зовнішнього API Open Food Facts |
| **Cumulative Layout Shift (CLS)** | 0.00 | 0.00 | Фіксовані розміри модальних елементів (`flex-shrink: 0`) |

#### 3. Висновки та виконані оптимізації

* **Debounce-фільтрація пошуку (350 мс):** зменшила кількість зайвих HTTP-запитів до `/api/fatsecret/search` під час набору тексту на ~70%.
* **Єдина роздача статики з Express:** у production-режимі зібраний клієнт (`frontend/dist`) віддається тим самим сервером, що виключає додаткові CORS preflight-запити (`OPTIONS`).
* **Аналіз різниці середовищ:** локальний сервер має мінімальну затримку мережі (TTFB < 25 мс), тоді як хмарний хостинг Render забезпечує публічну доступність по HTTPS (обов'язкову для доступу до камери сканера штрихкодів на мобільних пристроях), але має вищий TTFB через мережеву маршрутизацію та ефект «холодного старту» безкоштовного тарифу.

### Лабораторна робота №5. Безпека веб-застосунків

#### 1. Реалізовані механізми захисту в коді (`backend/server.js` та маршрути)

1. **Захист HTTP-заголовків (`Helmet`):** автоматично приховує заголовок `X-Powered-By`, встановлює `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN` (захист від Clickjacking) та політики реферера.
2. **Захист від DoS та brute-force (`express-rate-limit`):** обмеження частоти запитів до `/api` (максимум 400 запитів за 15-хвилинне вікно з одного IP) із поверненням статусу `429 Too Many Requests`.
3. **Захист сесій та Cookie:**
   * `httpOnly: true` — унеможливлює читання ідентифікатора сесії через `document.cookie` у разі XSS;
   * `sameSite: 'lax'` — базовий захист від міжсайтової підробки запитів (CSRF);
   * `secure: true` у production — передача cookie виключно шифрованим каналом HTTPS.
4. **Додатковий захист від CSRF:** власний middleware перевіряє заголовки `Origin` та `Referer` для всіх запитів, що змінюють стан сервера (`POST`, `PUT`, `PATCH`, `DELETE`), блокуючи сторонні домени статусом `403 Forbidden`.
5. **Захист від SQL-ін'єкцій та переповнення буфера:** використання **Prisma ORM** гарантує параметризацію всіх запитів до БД; розмір тіла JSON/URL-encoded запитів обмежено (`limit: '200kb'`).
6. **Валідація та санітизація вхідних даних:** у модулі штрихкодів (`/api/barcode/:code`) вхідний параметр очищується від нецифрових символів (`replace(/\D/g, '')`) і перевіряється на допустиму довжину (6–14 цифр) перед формуванням зовнішнього запиту (захист від SSRF / Path Traversal).
7. **Розмежування прав доступу (RBAC):** адміністративні маршрути перевіряють наявність ролі `ADMIN`, а операції видалення власних продуктів і рецептів виконуються з перевіркою належності запису поточному користувачу.

#### 2. Результати інструментальної та ручної перевірки безпеки

* **Автоматизований аудит залежностей (`npm audit`):** перевірено пакети `backend` та `frontend` на наявність відомих CVE-вразливостей; критичних вразливостей у production-залежностях не виявлено.
* **Перевірка конфігурації заголовків та HTTPS (Chrome DevTools / Lighthouse Best Practices):** підтверджено примусове використання HTTPS на Render, наявність захисних заголовків `Helmet` та відсутність витоку стектрейсів або службової інформації сервера у відповідях про помилки.
* **Ручне тестування типових векторів атак:**
  * *Неавторизований доступ до API:* прямі `POST`/`DELETE` запити до `/api/recipes` та `/api/custom-foods` без активної сесії відхиляються сервером.
  * *Спроба підробки міжсайтового запиту (CSRF):* надсилання `POST`-запиту зі стороннім заголовком `Origin: https://evil.example` коректно блокується з кодом `403`.
  * *Ін'єкції у параметри URL:* передача спецсимволів у `/api/barcode/../../etc/passwd` відфільтровується регулярним виразом та повертає помилку `400 Некоректний формат штрихкоду`.
  * *XSS у назвах продуктів і рецептів:* React автоматично екранує текстові вузли при рендерингу карток та списків, що унеможливлює виконання довільного JavaScript-коду.
